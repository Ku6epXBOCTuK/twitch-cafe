## Шаг 1. Оценка заказа: лишние дубликаты ингредиентов (баг «идеально»)

**Проблема.** `котлета + котлета + сыр` против рецепта `котлета + сыр`
засчитывается как «идеально»: в `order-validator.ts` `extra` считается как «слой
не входит в canonical» (`layers.filter((id) => !canonical.includes(id))`), а
дубль котлеты в canonical входит → не штрафуется. То же в `assessSimple`
(`layers.includes` вместо подсчёта).

**Решение.** Перейти на мультимножество (подсчёт количества):

- для каждого id: `countInTray - countInRecipe > 0` → лишние дубликаты,
  `countInRecipe - countInTray > 0` → не хватает;
- дубликаты штрафуются как `extra` (вес `COST_EXTRA`, слабое влияние — уже так в
  `scoring.ts`);
- `wrongOrder` для `ordered`-начинки: сравнение не-base слоёв с учётом удаления
  лишних дубликатов (сначала вычесть мультимножество, потом сравнить порядок
  остатка с canonical).
- `assessSimple`: подсчитать вхождения `item.id`, излишек — в `extra`.

**Файлы:** `src/lib/core/services/order-validator.ts` (+ тесты в
`order-validator.test.ts`: дубль котлеты, `котлета+котлета+сыр`, дубль base,
дубль в simple-предмете).

## Шаг 2. Состояние заказа после serve: `!заказ` и монитор исполнения

**Проблема (два бага из backlog).**

1. «!заказ не работает, после выполненного заказа следующий взятый не
   отображается на мониторе».
2. «после выполнения заказа он должен быть удалён у исполнителя — сейчас
   `!заказ` показывает последний заказ и пакет/поднос».

**Анализ.** После serve заказ остаётся в сессии со статусом `COMPLETED`, и:

- `getOrder()` возвращает завершённый заказ → `case "menu"` в `chat-commands.ts`
  отвечает старым заказом и подносом вместо «ты не в игре»;
- сессия с завершённым заказом остаётся в `sessions` — добавить тест на сценарий
  «serve → !взять новый → монитор показывает новый заказ» (воспроизвести баг
  «следующий взятый не отображается»).

**Решение.**

- В `chat-commands.ts` (`case "menu"`), `nextDish` и в проекторе считать
  «активный заказ» только при `status === PENDING`: добавить в `SessionManager`
  метод `getActiveOrder(username)` и использовать его вместо `getOrder` там, где
  подразумевается активный заказ.
- Ответ `!заказ` без активного заказа: «у тебя нет активного заказа» (новая
  реплика в `replies.ts`).
- Интеграционный тест: «serve → !взять → !заказ показывает новый заказ; монитор
  исполнения содержит новый заказ».

**Файлы:** `session-manager.ts`, `chat-commands.ts`, `replies.ts`,
`projector.ts` (+ тесты в `session-manager.test.ts`, `chat-commands.test.ts`,
`projector.test.ts`).

## Шаг 3. Уведомление о просроченном заказе + сгорание из монитора

**Проблема.** `onTimeout` молча ставит `EXPIRED` и снимает XP — в чат ничего не
приходит; backlog также отмечает, что истёкший заказ «долго не пропадает» с
монитора исполнения.

**Решение.**

- `SessionManager` не знает про чат — добавить колбэк уведомлений:
  `onTimeoutMessage?: (username: string, message: string) => void` (или
  расширить `ISimEvents`/ввести `SessionEvents`) и вызывать его из `onTimeout` с
  готовой репликой «{username}, время вышло — заказ сгорел (−50 XP)». В
  `chat-bot.ts` подписать колбэк на `client.say` в канал (берём все каналы или
  первый — решить при реализации).
- Пропадание из монитора: `projectExecution` фильтрует по `PENDING`, карточка
  исчезает при следующем кадре SSE (250 мс). Пункт «долго пропадает» проверить
  на плейтесте после шага; если воспроизводится — отдельная задача.
- Тест: `onTimeout` → вызвано уведомление с репликой; XP снят один раз.

**Файлы:** `session-manager.ts`, `chat-bot.ts` (+ тест в
`session-manager.test.ts`).

## Шаг 4. Спавн: заполнять все пустые слоты за тик

**Проблема.** `IncomingOrders.spawn()` кладёт только один заказ в первый пустой
слот за интервал (20 с) — доска заполняется медленно.

**Решение.** `spawn()` заполняет **все** пустые слоты за один вызов (каждому —
свой burn-таймер). Интервальный таймер спавна оставить: он задаёт паузу между
«волнами», а не между отдельными заказами. Замечание из backlog про «два игрока
и один заказ»: с текущей моделью взятия (`!взять N` по слотам) гонки нет — слот
атомарно обнуляется в `takeOrder`; интервальный спавн оставляем (предсказуемый
ритм для стрима).

**Файлы:** `incoming-orders.ts` (+ тест в `incoming-orders.test.ts`: после
одного `spawn()` доска заполнена полностью; burn-таймеры у всех).

## Шаг 5. Генерация заказов: заказы на 1–4 блюда

**Проблема.** `OrderFactory.generateOrder` создаёт ровно один item.

**Решение.**

- В `ORDER_CONFIG` добавить `ORDER_SIZE_WEIGHTS` (например,
  `[0.5, 0.3, 0.15, 0.05]` для 1–4 блюд) — открытая таблица, крутится на
  плейтестах.
- `generateOrder(rng)`: выбрать размер по весам, набрать блюда случайно
  (допускаются повторы блюда, как в тестах `COLA, COLA`).
- `timeLimit` масштабировать от числа блюд: `base * (1 + 0.5 * (n - 1))`
  (коэффициент в конфиг).
- Проверить смежное: `nextDish`/serve уже работают с любым числом блюд (тесты с
  двумя есть) — прогнать сценарий 4 блюд.

**Файлы:** `core/config.ts`, `services/order-factory.ts` (+ тесты: распределение
размеров, timeLimit растёт).

## Шаг 6. Оверлей: номер слота и исполнитель сверху таблички, звёздочки

**Проблема (три пункта backlog).**

1. Номер слота входящего заказа (1, 2, 3) — сверху таблички, а не внутри текста.
2. Монитор исполнения симметричен входящим: исполнитель — сверху таблички, а не
   первой строкой внутри.
3. Придирчивость отображать звёздочками (сейчас «придирчивость 0.5/5» — и это
   ещё и неправильно: strictness 0..1 выводится как «/5» без пересчёта).

**Решение.**

- В `pixi-boards.ts`: у слота — отдельный `Text`-заголовок над карточкой (для
  incoming — номер слота; для execution — ник исполнителя), контент карточки —
  без этих строк.
- Звёзды: считать на бекенде в `projector.ts`
  (`Math.max(1, Math.round(strictness * 5))`) — фронт остаётся тупым; в
  `IncomingOrder` добавить `stars: number`, рендер `★`/`☆` в `pixi-boards.ts`.
- Тесты в `projector.test.ts` на `stars`.

**Файлы:** `overlay/types.ts`, `projector.ts`, `pixi-boards.ts` (+ тесты
проектора; рендер проверяем вручную в dev).

## Шаг 7. Короткие названия команд: определение по префиксу

**Проблема.** Команды приходится писать целиком (`!положи`, `!взять`,
`!отдать`…). Хочется, чтобы валидная команда определялась **автоматически** по
неполному названию: `!по`, `!пол`, `!поло`, `!полож`, `!положи` — всё это put, и
так для любой команды. Без хардкода коротких алиасов: механизм должен работать
для любых имён в `COMMANDS`, включая те, что добавим позже.

**Решение.**

- В `command-parser.ts` резолв токена — чистая функция
  `resolveCommandKind(token, commands)` (легко тестировать отдельно):
  1. **Точное совпадение** с алиасом → этот kind (приоритет; обратная
     совместимость).
  2. Иначе **префиксный матчинг**: алиасы, начинающиеся с токена
     (`alias.startsWith(token)`) → множество их kinds:
     - ровно один kind → используем его (`!по`, `!пол`, `!поло`, `!полож` → put;
       аргумент `rest` дальше идёт в put/recipe/take как сейчас);
     - несколько разных kinds → неоднозначно, **молча игнорируем** (без ответа в
       чат: реплики-флуд уйдут в переделку на универсальные события для
       проектора/оверлея, там и решим);
     - ноль → как сейчас: `null`, игнор.
- **Минимум 2 символа**: команды резолвятся начиная с двух символов после `!`;
  токен короче (один символ) — скипаем (однобуквенные `!п`/`!в` слишком легко
  получить случайно, а пользы в них нет). Точные совпадения с односимвольным
  алиасом всё равно нет — в `COMMANDS` таких нет.
- Токен уже приводится к lowercase; матчинг только по токену команды, аргументы
  не участвуют (`!пол сыр` → put + «сыр»; `!вз 1`, `!взя 2` — работают сами
  собой).
- Побочный бонус: короткие латинские вводы (`!pu` → put, `!ta` → take) тоже
  начинают работать — это ок.
- В подсказках оверлея пометка «команды можно писать сокращённо (первые буквы):
  !пол, !вз…» + поправить опечатки («добавть», «ингридиент»).
- Тесты: `!по/!пол/!поло/!полож/!положи сыр` → put; `!вз 1`, `!взя 2` → take;
  `!от` → serve; `!да` → next; `!за` → menu; `!ре` → recipe; `!му` → bin; точное
  совпадение приоритетно; неоднозначный префикс (синтетический набор команд в
  тесте резолвера) → `null` без исключений; неизвестное → `null`; односимвольный
  токен (`!п`, `!p`) → `null`.

**Файлы:** `twitch/command-parser.ts` (резолвер), `twitch/command-hints.ts`
(пометка про сокращения) + тесты `command-parser.test.ts`,
`command-hints.test.ts`.

## Шаг 8. Двойное подключение бота при HMR (dev)

**Проблема.** При обновлениях бот подключается второй раз — вероятно, только в
dev из-за HMR: `hooks.server.ts` перезагружается, но модуль-синглтон
`bootstrap.ts` / старый `ChatClient` остаются в памяти.

**Решение.**

- Guard на уровне `globalThis` (устойчив к перезагрузке модуля): хранить `game`
  и клиент бота в `globalThis.__twitchCafe__`; при повторной инициализации —
  disconnect старого клиента перед подключением нового.
- Проверить в dev: `pnpm dev`, правка файла → в логах одно «бот подключён».

**Файлы:** `core/game/bootstrap.ts`, `twitch/bootstrap.ts`, `hooks.server.ts`.

# ADR: начать миграцию на Effect v4 RC

- **Статус:** proposed
- **Дата:** 2026-09-23
- **Решение:** использовать `effect@4.0.0-rc.117`

## Контекст

Проект переходит от ручного управления таймерами, singleton runtime и
`{ ok: boolean, ... }` к системе с явным lifecycle, контролируемыми ошибками и
детерминированными тестами. Effect рассматривается как инфраструктурный слой для
этих свойств, а не как замена чистых доменных функций.

## Решение

1. Начать миграцию на pinned `effect@4.0.0-rc.117`.
2. Не использовать floating-диапазон версий и автоматически обновлять RC.
3. Не подключать модули из `effect/unstable`, если они не нужны для выбранной
   архитектуры.
4. Сначала подтвердить минимальным smoke-тестом работу `Effect.gen`, `Schema`,
   `Scope`, `Layer` и `TestClock` в текущем SvelteKit/Vite стеке.
5. После успешного smoke-теста переходить к `GameRuntime` и затем к миграции
   lifecycle по вертикальным срезам.
6. Если smoke-тест не проходит, остановиться и принять отдельное решение; не
   переключаться автоматически на Effect 3.x.

## Границы пилота

Пилот не меняет игровые правила, scoring, тексты реплик и публичное поведение
команд. В нём допускаются только:

- зависимость и lockfile;
- compatibility-smoke test;
- ADR и связанная документация;
- проверки `pnpm test`, `pnpm check`, `pnpm lint` и `pnpm build`.

## Последствия

Плюсы:

- проверяется совместимость до изменения runtime;
- фиксируется API v4, на который рассчитаны следующие этапы;
- миграция начинается с измеримого риска, а не с полного переписывания.

Риски:

- RC API может измениться в следующей версии;
- production build может выявить bundler или SSR-проблемы позже;
- слишком широкий первый этап усложнит ревью.

## Условия принятия

- smoke-тест проходит без реального ожидания времени;
- lockfile содержит точную версию RC;
- все baseline-проверки проходят;
- пользователь подтверждает результат до начала миграции `GameRuntime`.

## Следующее решение

После ревью пилота отдельно согласовать `GameRuntime`, production/test `Layer` и
место хранения состояния сессий.

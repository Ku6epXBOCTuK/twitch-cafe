## 2. Игра в текущем состоянии

### Игровой цикл

1. На доске входящих появляются автоматически сгенерированные заказы. Сейчас
   есть три слота, интервал спавна — 20 секунд, срок жизни невзятого заказа — 60
   секунд.
2. Игрок забирает заказ командой `!взять N` или `!take N`, где `N` — номер слота
   от 1 до 3. У игрока может быть один активный заказ.
3. Игрок кладёт ингредиенты на поднос командой `!put`.
4. Если в заказе несколько блюд, `!next` запечатывает текущее блюдо и очищает
   поднос. Последнее блюдо запечатывать не нужно: его можно сразу сдать.
5. `!serve` оценивает заказ, начисляет или снимает XP. Следующий заказ
   автоматически не выдаётся: игрок сам берёт новый заказ с доски.
6. `!bin` очищает поднос, `!menu`/`!заказ` показывает состояние заказа,
   `!рецепт <блюдо>` открывает рецепт.

### Текущие команды

- Взятие: `!взять <1-3>` / `!take <1-3>`.
- Сборка: `!put <ингредиент>` / `!add` / `!положи`.
- Запечатывание: `!next` / `!дальше`.
- Сдача: `!serve` / `!submit` / `!отдать`.
- Очистка: `!bin` / `!мусор`.
- Просмотр заказа: `!menu` / `!заказ` / `!order`.
- Рецепт: `!рецепт <блюдо>` / `!recipe <блюдо>`.

Короткие префиксы команд пока не поддерживаются. Реализован поиск ингредиентов и
блюд по полному имени или его части.

## 3. Что уже реализовано

| Область                  | Состояние         | Фактическое состояние                                                                                             |
| ------------------------ | ----------------- | ----------------------------------------------------------------------------------------------------------------- |
| Входящие заказы          | Работает          | `IncomingOrders` создаёт заказы Effect-fiber циклом, хранит слоты и снимает burn-таймеры через scope.             |
| Взятие и multi-dish flow | Работает          | Effect-операции `takeOrderEffect`/`nextDishEffect`, sealed/current dishes и `!next`; terminal state изолирован.   |
| Оценка                   | Работает частично | Есть missing/extra/order issues, rating, verdict и XP; дубликаты ингредиентов пока не учитываются как количества. |
| Команды Twitch           | Работает          | Есть русские/английские алиасы, Effect-boundary, `GameEvent`, correlation id и сценарии чата.                     |
| SIM-шов                  | Работает          | `ISimPort`, bounded event queue и `StubSim` реализуют мгновенный игровой цикл.                                    |
| Настоящий SIM            | Не реализован     | `miniplex` установлен, но мир, тик и движение не подключены.                                                      |
| Проекция и SSE           | Работает          | `GameRuntime.events` — bounded event stream; snapshot только для initial/replay, SSE без polling.                 |
| Pixi overlay             | Работает частично | Есть сцена и мониторы; координаты игроков, звёзды, часть заголовков и lifecycle требуют доработки.                |
| Тесты и проверки         | Работает          | Есть Vitest, Svelte check, ESLint, Prettier и `check:legacy`.                                                     |

## 4. Архитектура

Игра разделена на три слоя:

```text
RULE CORE   — заказы, валидация, scoring, сессии и XP
SIM         — абстракция действий и будущая физика персонажей
PROJECTION  — projector, SSE и Pixi-визуализация
```

### RULE CORE

Отвечает за:

- типы заказа, блюда, ингредиента и рецепта;
- `OrderFactory`;
- `OrderValidator` и таблицу весов `scoring.ts`;
- `SessionManager`, таймеры заказа, XP и состояние сессий;
- `IncomingOrders` и `RecipeBook`.

### SIM-шов

`ISimPort` отделяет чат и правила от конкретной реализации движения. Сейчас
`src/lib/sim/sync.ts` подключает `StubSim`: команды применяются мгновенно и
возвращаются через bounded event queue с `ACTION_COMPLETED`. Настоящий
miniplex-мир, `world.ts`, `simulation.ts` и системы движения остаются отдельной
будущей задачей, а не частью текущего MVP.

### PROJECTION

`projector.ts` получает `SessionSnapshot` из события runtime и строит
`OverlaySnapshot`. `GameRuntime.events` отдаёт initial replay и последующие
`SessionChangedEvent` через `Stream`; SSE-роут не polls и не вычисляет игровые
решения. Фронт не принимает решения и не изменяет игровое состояние.

## 5. Зафиксированные контракты

- `IRecipe.fillingOrder` имеет значения `ordered` и `unordered`. Положение base
  выводится из ингредиентов с категорией `base`; отдельный флаг base в рецепте
  не нужен.
- `IOrder.items` — массив `IOrderItem`; блюдо может быть `PENDING` или `SEALED`.
  Оценка идёт по запечатанным блюдам и текущему подносу.
- Статусы заказа — `PENDING`, `COMPLETED`, `EXPIRED`, `FAILED`. `EXPIRED`
  применяется и к сгоревшему входящему заказу, и к заказу игрока по таймауту.
- `strictness` хранится как скаляр `0..1`. Отображение звёздами — отдельная
  функция проекции, а не часть типа клиента.
- `takeOrderEffect` — единственный production-способ начать заказ.
  Автоматическая выдача следующего заказа после `serve` отменена решением O1.
- `!next` очищает поднос через `ISimPort.clearTray`; смена статуса заказа сама
  по себе не должна оставлять старый заказ активным в UI.
- Сессия хранит XP после завершения заказа, но активным считается только заказ в
  статусе `PENDING`.

## 6. Известные расхождения и ограничения

1. **Оценка дубликатов:** `assessSimple` и `assessComposite` используют
   `includes`/фильтрацию, поэтому лишняя котлета или второй Cola не всегда
   попадают в `extra`.
2. **Состояние после `serve`:** `SessionManager` сохраняет заказ в сессии, а
   `getOrder()` не фильтрует статус. Это может привести к старому ответу
   `!заказ` и неверному поведению команд после завершения.
3. **Таймеры:** входящий заказ живёт 60 секунд, взятый заказ получает новый
   таймер на 90 секунд, но projector считает оба дедлайна от `createdAt`. Перед
   изменением таймеров нужно зафиксировать единый контракт.
4. **Генерация:** `OrderFactory` сейчас всегда создаёт один `IOrderItem`, а
   размер группы и распределение порций для заказа на 1–4 человек ещё не
   представлены.
5. **Строгий overlay:** `strictness` выводится на доске как `0.5/5`, хотя
   backend хранит `0..1`; координаты игроков остаются `(0, 0)`.
6. **Событийная модель:** SSE уже подписан на `GameRuntime.events`; анимации и
   проактивные уведомления отложены.
7. **HMR:** bootstrap хранит runtime в module-local переменной, а клиент бота не
   гарантированно отключается при повторной инициализации в dev.
8. **Состояние в памяти:** XP, сессии и заказы сбрасываются при перезапуске;
   постоянного хранилища и удаления отключившихся игроков нет.

## 7. Целевой порядок развития

Подробные критерии и файлы находятся в [`backlog.md`](backlog.md). Общий
порядок:

1. **Корректность:** дубликаты, активный заказ после `serve`, защита команд от
   terminal-состояния, таймаут и дедлайны.
2. **Быстрые улучшения:** HMR, заполнение слотов, короткие команды, мелкие
   исправления overlay.
3. **Контент:** генерация заказов для 1–4 человек с дополнительными порциями и
   расширение меню только после стабилизации правил.
4. **Настоящий SIM:** miniplex, движение, станции, snapshot и визуализация
   игроков.
5. **События и эксплуатация:** проактивные уведомления, OBS Browser Sources и
   production-конфигурация.

Критерий готовности каждого изменения: `pnpm test`, `pnpm check` и `pnpm lint`
проходят; для изменений сборки/запуска дополнительно проверяется `pnpm build`.

## 8. Что считать устаревшим

Следующие утверждения из старых документов больше не являются планом:

- `!join` и `!start` как способ начать игру — заменены на `!взять`/`!take` по
  номеру слота.
- Автоматическая выдача следующего заказа после `serve` — отменена.
- Плоская модель `IOrder.items: IMenuItem[]` — заменена на `IOrderItem` и
  `SEALED/PENDING`.
- Флаг `RECIPE_MODE` — заменён на `fillingOrder`.
- Статус `CANCELLED` — заменён на `EXPIRED`.
- Пункты `docs/archive/sim.md` о готовом miniplex-мире — описывают цель, а не
  текущую реализацию; фактический production-путь использует `StubSim`.
- Стабильные FIFO-слоты execution-монитора — не реализованы; текущий projector
  выводит активные сессии в порядке взятия.
- `strictness` как шкала `0–5` в backend — неверно; backend использует `0..1`,
  шкала отображения должна вычисляться отдельно.

Старые документы можно читать для истории решений, но новые задачи следует
добавлять только в `backlog.md`.

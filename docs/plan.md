# План реализации ядра: сборка заказов из чата Twitch

## 1. Данные (Модель данных)

### Ингредиенты (`IIngredient`)

Каждая базовая сущность (котлета, булочка, сыр, стакан, соус) имеет:

- `id` и `name`
- `category` (мясо, овощи, соус, база и т.д.)
- `visualAsset` (ссылка на спрайт/иконку для оверлея)

Категория `base` важна для логики «снаружи булки» (см. валидацию).

### Предметы меню (`IMenuItem`)

Все, что клиент может заказать, делится на два основных типа (в коде:
`variant: 'simple' | 'composite'`):

- **Простой предмет (`IMenuItemSimple`)**: Напиток, фри, соус в соуснике.
  Свойства: `id`, `name`, `variant: 'simple'`.
- **Составной предмет (`IMenuItemComposite`)**: Бургер, пицца, хот-дог.
  Свойства: `id`, `name`, `variant: 'composite'`, `recipe: IRecipe`.

### Рецепты (`IRecipe`)

- `id`, `name`
- `ingredients: IIngredient[]` — **канонический** список ингредиентов (то, как
  блюдо собрано «правильно»). Для бургера: [нижняя булочка, котлета, сыр,
  верхняя булочка].
- `fillingOrder: 'ordered' | 'unordered'` — **структурное свойство блюда**
  (одинаково для всех клиентов): порядок **не-base начинки**.
  - **`ordered`** — порядок начинки значим: бургер (патти → сыр), хот-дог
    (сосиска внутри). Проверяется с жёсткостью по `strictness` клиента.
  - **`unordered`** — порядок начинки неважен: топпинги пиццы, салат. Не
    проверяется **ни при каком клиенте**, даже для гурмана. Хаос начинки
    разрешён (это смешно) и не усложняет оценку — флаг просто отключает штраф за
    порядок.

**База** — отдельного флага нет. Положение базы **выводится из рецепта**: базы =
ингредиенты категории `base` (одна → вниз; две → низ и верх; ноль → базы нет). А
вот **насколько критично** нарушить положение базы — решает `strictness`
клиента: easygoing почти прощает базу не на месте, `normal`/гурман считают
критичным (формула в «Логике оценки сборки»). Жёсткой обязательности «для всех»
у базы нет — она штрафуется, как и всё остальное, через `strictness`.

`fillingOrder` — структурное свойство **блюда** (что _вообще_ можно штрафовать),
`strictness` — свойство **клиента** (насколько сильно это кусает в `rating`).
Это две независимые оси.

_Примечание по коду: в `src/lib/core/types/recipe.ts` сейчас флаг `RECIPE_MODE`
(`STRICT/LOOSE`) — заменить на `fillingOrder`. Базу отдельно не храним, она
выводится из ингредиентов категории `base`._

### Клиенты (`ICustomer`)

У каждого заказа есть свой клиент. `strictness` — **непрерывный скаляр `0..1`**:
порог толерантности клиента к отклонению от идеальной сборки. `0` — совсем не
придирчив, `1` — гурман, требует идеала.

**Важно:** `strictness` — про **отношение клиента** (насколько сильно отклонения
«кусают» в `rating`), а не про устройство блюда. `fillingOrder` рецепта задаёт,
проверять ли порядок начинки; база и её положение выводятся из рецепта; а
`strictness` определяет, насколько критично любое нарушение — включая базу не на
месте (easygoing почти прощает, `normal`/гурман — нет). Формула — в «Логике
оценки сборки».

- `id`, `name`
- `strictness: number` — `0..1`

Именованные архетипы — это просто **пресеты скаляра** (для реплик в чат и
генерации заказов), а не отдельные механики:

```ts
customers.ts:
  easygoing: { name: 'Добряк',  strictness: 0.2 }
  normal:    { name: 'Обычный', strictness: 0.5 }
  picky:     { name: 'Гурман',  strictness: 0.9 }
// или генерировать непрерывно: strictness = 0.2 + 0.7 * (сложность)
```

### Заказ (`IOrder`)

- `id` заказа
- `items: IMenuItem[]` — список требуемых предметов
- `customer: ICustomer` — кто заказывает, определяет порог требовательности
- `timeLimit` — ограничение по времени (таймер)
- `createdAt` — метка выдачи заказа
- `status: 'pending' | 'completed' | 'expired' | 'failed'` (в коде сейчас
  `PENDING | COMPLETED | CANCELLED | FAILED` — привести к доке, добавить
  `expired`)

### Сессия игрока (`PlayerSession`)

Учётная запись игрока (RULE CORE): активный заказ, опыт, уровень. **Физическое
состояние персонажа** (позиция, `busy`/занятость, очередь действий) живёт в
сущности SIM, а не здесь (см. «Симуляция персонажей»).

- `order`, `timer` — активный заказ и его таймер
- `xp`, `level` — опыт и уровень зрителя (см. оценку)
- `simEntityId` — ссылка на сущность-персонажа в SIM (связь учётки и физики)

## 2. Архитектура

Игра делится на **три слоя**: чистые правила, симуляция персонажей и проекция.

```txt
RULE CORE   — правила игры (детерминированные, без позиций и сети)
SIM         — бекенд-симуляция персонажей (миниплекс/ECS)
PROJECTION  — фронт: оверлей OBS (только визуализация снапшота SIM)
```

- **RULE CORE** — правила: что валидно, сколько XP, какой вердикт. Никаких
  позиций и таймеров. Полностью юнит-тестируется чистыми функциями:
  `assessOrder(tray, order)` не требует запущенного мира.
- **SIM** — **настоящая симуляция на бекенде**: персонажи физически ходят по
  кухне, ждут очереди у станций, могут застревать в толкучке. Это источник
  правды по позициям и по **моменту завершения действия** — застрявший в проходе
  персонаж не донесёт поднос вовремя, а это пространственный результат, а не
  таймер. Построено на ECS (`miniplex`).
- **PROJECTION** — оверлей: читает снапшот SIM и события, рисует картинку.
  Логики и физики на фронте нет.

Между слоями — **событийный шов** (`sim/sync.ts`, см. «Асинхронная модель
действий»): ни SIM, ни PROJECTION не пишут одну правду дважды — все переходы
через события, а учётка (RULE CORE) только реагирует на события SIM.

```txt
src/lib/core/                — RULE CORE: правила игры (без позиций)
  types/                     — интерфейсы (ingredient, menu_item, recipe, order, customer, tray)
  data/
    menu.ts                  — статичный каталог ингредиентов и пунктов меню
    customers.ts             — профили клиентов (easygoing/normal/picky)
  services/
    order-validator.ts       — оценка сборки относительно заказа и клиента
    order-factory.ts         — генератор заказов (+ случайный клиент)
    scoring.ts               — вердикт и XP (штрафы/награды)
  game/
    session-manager.ts       — учётка игроков: сессии, XP, уровни, реестр
src/lib/sim/                 — SIM: симуляция персонажей (миниплекс/ECS)
  world.ts                   — мир, сущности и компоненты
  systems/
    move.ts                  — движение по пути, обход станций
    interact.ts              — старт/завершение действий у станций
    congestion.ts            — толкучка/застревание в проходах
    actions.ts               — жизненный цикл PlayerAction (очередь, тайминги)
  sync.ts                    — события между SIM и RULE CORE (шов)
src/lib/twitch/              — интеграция с Twitch
  chat-bot.ts                — подключение (@twurple/chat), подписка на onMessage
  command-parser.ts          — разбор сообщений чата → заявки в SIM
  replies.ts                 — формирование ответов в чат
src/routes/+page.svelte      — PROJECTION: оверлей состояния стрима (OBS)
```

_Изменение относительно прежнего плана:_ `assembly-station.ts` и
`action-queue.ts` переезжают в SIM — очередь и тайминги действий определяются
физикой (см. «Асинхронная модель действий»). Объёмный трей со слоями хранится в
SIM как данные сущности-подноса; `OrderValidator` получает его снимок.
`SessionManager` остаётся в RULE CORE как учётка.

## 3. Ключевые классы и их зоны ответственности

### `OrderFactory` (Генератор заказов)

- **Задача:** создавать случайные или сценарные заказы в зависимости от уровня
  игры.
- **Методы:**
  - `generateOrder(difficultyLevel, menu, customers)` — выбирает случайные
    предметы из доступного меню и **случайного клиента** (чем выше уровень — тем
    выше шанс придирчивого), возвращает `IOrder`. Рассчитывает `timeLimit` от
    сложности.

### `SessionManager` (Учётка игроков — RULE CORE)

Игра чатовая, поэтому у каждого зрителя своя сессия:
`Map<username, PlayerSession>`. Здесь **учётка**: активный заказ, XP, уровень.
Физика персонажа — в SIM, связь — через события `sim/sync.ts`.

- `startOrder(username, difficulty)` — выдать зрителю заказ через `OrderFactory`
  и сообщить SIM (`START_ORDER`), чтобы у зрителя появился персонаж-сущность с
  этим заказом.
- `putIngredient(username, ingredientId)` / `resetTray(username)` /
  `serve(username)` — это **заявки из чата**: ставятся персонажу в SIM как
  задачи (`!put` → `fetch`+`place`, `!bin` → `bin`, `!serve` → `serve`). Что и
  когда реально произойдёт, решает SIM (персонаж идёт/ждёт/застревает). Порядок
  завершённых `place` = порядок слоёв в `tray.layers` (важно для `picky`).
- `onActionCompleted(username, action)` — обработка события SIM: фиксирует, что
  действие кончилось; по завершённом `serve` берёт замороженный снимок
  `tray.layers` → `OrderValidator` → `scoring.ts` → применить `xpDelta`
  (начислить/снять опыт) → выдать следующий заказ или отстранить.
- `onTimeout(username)` — автофейл при истечении `timeLimit` (таймер в учётке, с
  очисткой после завершения). Таймаут = плохая сдача (снятие XP). Идемпотентен:
  если поднос уже передан — игнор.

### Асинхронная модель действий (жизненный цикл в SIM)

Все действия игрока **асинхронны**: персонаж физически идёт за ингредиентом,
собирает бургер, несёт поднос. Мгновенных изменений состояния нет — и **время
каждого действия определяет SIM**, потому что оно зависит от физики (расстояние
по пути, скорость, толкучка). Чистого `setTimeout` недостаточно: застрявший в
проходе персонаж не донесёт поднос вовремя. Поэтому очередь и тайминги живут в
SIM (`actions.ts`), а не в ядре.

- `PlayerAction = { kind: 'fetch' | 'place' | 'serve' | 'bin'; ingredient?: IIngredient; duration: number; startedAt: number }`.
- Заявки игрока из чата (`!put`, `!serve`, `!bin`) становятся задачами, которые
  SIM ставит персонажу в очередь. По мере продвижения по путям и завершения
  взаимодействий SIM определяет фактические `startedAt`/`duration` и по
  окончании шлёт событие `ACTION_COMPLETED` в учётку.
- Пока персонаж занят (`busyUntil > now`), новые команды либо встают в очередь,
  либо отклоняются с ответом «персонаж ещё идёт» (политика настраивается).
- `duration` считается от **расстояния по пути** до полки/станции и скорости
  персонажа; скорость зависит от уровня. Влияние толкучки и застреваний — внутри
  SIM (`congestion.ts`).
- Оверлей рисует прогресс/анимацию **только по снапшоту и событиям SIM**
  (`startedAt`, `duration`, `kind`), чтобы чат и оверлей не расходились:
  источник правды один — SIM.

### `OrderValidator` (Оценка заказа)

Самый главный класс игровой логики. **Не «годен/не годен», а примерная оценка
качества** — зрители могут собрать вообще не то и отдать.

- **Методы:**
  - `assessItem(assembled, targetMenuItem, customer)` — оценивает одно блюдо по
    шкале `0..1` (см. формулу в разделе 4).
  - `assessOrder(tray, order)` — усредняет оценку по всем позициям заказа.
  - Возвращает структурный результат:

  ```txt
  AssessmentResult {
    rating: 0..1,                    // доля «правильности» сборки
    verdict: 'perfect' | 'good' | 'ok' | 'bad' | 'awful',
    missing: IIngredient[],          // чего не хватает
    extra: IIngredient[],            // что лишнее
    orderIssues: string[],           // проблемы с порядком/слоями (напр. «булка не сверху»)
    xpDelta: number                  // ±XP, выводится из rating
  }
  ```

  Из `missing/extra/orderIssues` шьются ответы в чат («не хватает сыра», «булка
  не снаружи — заказчик фыркнул»).

### `scoring.ts` (Вердикт и опыт)

- Хранит **таблицу весов** `COST_MISSING / COST_EXTRA / COST_ORDER / COST_BASE`
  и формулу `rating` — единственное место, где крутится баланс на плейтестах.
- Из `rating` **выводит** `verdict` порогами (например: `>= 0.9` perfect,
  `>= 0.7` good, `>= 0.4` ok, `> 0` bad, `0` awful). `verdict` не хранится —
  нужен только для реплик в чат.
- `xpDelta` считается из `rating` (награды/штрафы конфигурируемы и привязаны к
  уровню игры).

### `CommandParser` (Разбор чата)

Строгий грамматический разбор, чтобы не парсить болтовню чата.

### `ChatBot` (Интеграция)

Подключение через `@twurple/chat`, подписка на `onMessage`, мэппинг сообщений →
`CommandParser` → заявки в SIM → события в `SessionManager` → ответы через
`replies.ts`.

## 4. Логика оценки сборки (Как сравнивать)

Оценка каждого блюда — `rating ∈ [0, 1]`. Стартуем с `1` и штрафуем по **формуле
с весами** (веса — конфигурируемая таблица в `scoring.ts`, крутится на
плейтестах). Затем усредняем по заказу.

**Две независимые оси** (не путать, не заменяют друг друга):

- **Структура блюда** — `fillingOrder` + база (выводится из ингредиентов
  категории `base`), одинаковы для всех клиентов: _что вообще_ штрафуется.
- **Вкус клиента** — `customer.strictness ∈ [0,1]`: _насколько сильно_ это
  кусает в `rating`.

### Формула (одно место правок — таблица весов)

```ts
// costs — конфигурируемые веса из scoring.ts
rating =
  1 -
  missing.count * COST_MISSING * (0.25 + 0.75 * strictness) - // сильнее у гурмана
  extra.count * COST_EXTRA * (0.25 + 0.75 * strictness) -
  wrongOrderCount * COST_ORDER * strictness - // 0, если fillingOrder='unordered'
  baseViolations * COST_BASE * strictness; // easygoing прощает, normal/гурман — критично
rating = clamp01(rating);
```

- `wrongOrderCount` считаем только при `fillingOrder === 'ordered'` (сравнение
  по индексам не-base позиций против каноничного рецепта). При `unordered` — 0.
- `baseViolations` — база не на нижнем слое (а при двух базах — и не на
  верхнем). У упорядоченных (`ordered`) база уже покрыта порядком, поэтому
  отдельно её считаем только у **неупорядоченных** (`unordered`) — напр. пицца:
  тесто внизу. Штраф за базу, как и везде, скалируется `strictness`.
- `COST_*` и сам вид формулы — открытая таблица: подгоняем эмпирикой плейтестов,
  а не фиксируем раз навсегда. Вес `COST_BASE` настраиваем так, чтобы при
  строгости среднего и выше нарушение базы утаскивало `rating` в `bad`.

### Как ложатся блюда

| блюдо       | fillingOrder | что допускает игрок / что штрафуется                                                 |
| ----------- | ------------ | ------------------------------------------------------------------------------------ |
| **Пицца**   | unordered    | начинка в любом порядке; тесто внизу — easygoing почти прощает, гурману критично.    |
| **Бургер**  | ordered      | булки снаружи / начинка по индексам — гурману критично; easygoing почти всё прощает. |
| **Хот-дог** | ordered      | сосиска внутри булки — гурману критично, easygoing прощает.                          |
| **Салат**   | unordered    | чистое мультимножество, базы нет.                                                    |

### Остальные правила

1. **Простой предмет (`IMenuItemSimple`):** совпадение ID. Правильный напиток →
   `rating 1`; не тот → `0` (клиенту дали не то, он в недоумении). Лишние
   предметы на подносе — штраф за `extra`.
2. **Составной предмет** — оценивается по формуле выше на основе `fillingOrder`
   и базы из рецепта.
3. **Итоговый `rating` заказа** — среднее по `items`; `verdict` и `xpDelta`
   **выводятся** из него (см. `scoring.ts`).

_Учитывая, что `tray` собирается командами чата, порядок слоёв = порядок команд
игрока._

## 5. Команды чата

- `!join` / `!start` — записаться в игру, получить свой заказ.
- `!put <ингредиент>` — поставить в очередь действие: персонаж идёт и кладёт
  ингредиент на поднос (алиасы: `!add`, `!положи`).
- `!serve` / `!submit` — отдать поднос на проверку (получить оценку и ±XP).
- `!bin` — сбросить поднос в мусорку.
- `!menu` — показать свой заказ и список доступного.

Всё остальное игнорируется; обрабатываются только сообщения от активных игроков.

## 6. Оверлей — PROJECTION (фронт, только визуализация)

SvelteKit-страница — не про ввод, а про **отображение состояния стрима**: кто
играет, у кого какой заказ и клиент, таймеры, XP. Плюс **визуализация
персонажей**: они ходят за ингредиентами, собирают бургеры, уносят подносы.

Оверлей **ничего не решает**: ни логики, ни физики на фронте нет. Он читает
снапшот SIM (позиции, текущие `PlayerAction`) и события (`ACTION_COMPLETED`) и
рисует по ним. Вся игровая логика и симуляция — на бекенде (RULE CORE + SIM),
поэтому оверлей можно менять/перерисовать, не трогая правила. Выводится поверх
стрима в OBS.

## 7. Порядок работ

1. **RULE CORE:** типы → каталог меню и профили клиентов (непрерывный
   `strictness` + пресеты) → `OrderValidator` (`fillingOrder` + база из рецепта,
   всё штрафуется через `strictness`) → `scoring.ts` (таблица весов, `verdict`
   из `rating`) → `OrderFactory`. Без позиций и сети, полностью юнит-тестируемо.
2. **SIM:** добавить `miniplex` → мир `world.ts` (сущности
